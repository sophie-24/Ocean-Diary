# OCEAN DIARY (가칭) — 1차 MVP 착수 패키지

**문서 목적:** 바로 저장소를 만들고 개발을 시작할 수 있도록 제품 범위, 사용자 흐름, 데이터/API 초안, 기술 구조와 첫 주 작업을 한곳에 고정한다.  
**대상 사용자:** 국내 스쿠버다이버  
**출시 형태:** iOS·Android 모바일 앱  
**핵심 경험:** 사진 업로드 → AI 해양생물 식별 후보 제시 → 사용자 확인/수정 → 종별 그림책 스타일 카드 → 도감에 발견 기록 저장

## 0. 이번 착수의 기본값

- 임시 서비스명은 **OCEAN DIARY**로 쓴다. 패키지명·도메인 등 변경 비용이 큰 이름에는 `ocean-diary`를 쓰고, 앱에 보이는 이름은 설정으로 바꿀 수 있게 둔다.
- 앱은 **React Native + Expo + TypeScript**로 iOS·Android를 함께 만든다. 화면을 빠르게 만들고 기기 카메라/사진 선택 기능을 연결하기 쉽다.
- 서버는 사용자의 서버 개발 경험을 활용해 **기존에 익숙한 프레임워크가 있다면 그것을 우선**한다. 새 프로젝트 기본값은 **FastAPI + PostgreSQL**이다. API 계약과 도메인 경계를 지키면 추후 교체 가능하다.
- 앱 첫 실행은 로그인 없이도 데모 도감과 샘플 흐름을 볼 수 있게 한다. 저장할 때는 계정 로그인을 요구한다. 초기 인증은 이메일 매직 링크 또는 이메일/비밀번호 중 팀이 구현하기 쉬운 한 방식으로 선택한다. 소셜 로그인은 MVP 필수 아님.
- 식별 결과는 확정 답이 아니라 **후보와 신뢰도**다. 사용자는 항상 직접 확인하며, 저신뢰 결과는 수동 검색/미확인 종 저장 경로를 제공한다.
- 첫 버전에서 촬영 장소는 선택 사항으로 두며, 사진의 GPS EXIF는 기본 제거한다. 정확한 위치는 받지 않고 국가/지역 정도만 사용자가 직접 입력하거나 생략한다.
- 초기 카탈로그는 우선 **국내 다이빙에서 만날 가능성이 높은 30종**으로 시작한다. 종 데이터와 그림책 스타일 대표 일러스트의 사용권을 확인한 뒤 공개한다.

## 1. 제품 개요 및 범위

### 제품 개요

OCEAN DIARY는 다이버가 찍은 수중 사진에서 만난 해양생물의 이름을 확인하고, 발견을 그림책 느낌의 종 카드와 개인 도감 기록으로 모으는 앱이다. AI는 식별을 돕지만 종의 최종 선택은 사용자가 한다. 도감의 종별 대표 일러스트는 공통이며, 같은 종을 다시 만나면 새 발견 기록이 쌓인다.

**사용자 가치:** 갤러리에 흩어져 있던 다이빙 사진을 “무엇을 만났는지” 확인하고 다시 찾아볼 수 있는 개인 해양생물 도감으로 바꾼다.

### MVP 포함

1. 계정 생성/로그인, 로그아웃 및 내 데이터 삭제 요청 진입점
2. 사진 1장 선택·촬영, 크기/형식 검증, 업로드 진행/실패 복구
3. AI 식별 작업 생성, 상태 확인, 상위 최대 3개 후보 표시
4. 후보 확인, 다른 종 검색/선택, 미확인으로 저장
5. 종 상세 카드(국문명, 학명, 짧은 설명, 대표 그림책 일러스트)
6. 발견 기록 저장 및 개인 도감 목록/상세 보기
7. 동일 종을 다시 저장하면 기존 종 항목 아래 발견 횟수와 기록이 증가
8. 사진 삭제 및 발견 기록 삭제
9. 기본 오류/빈 화면/로딩/네트워크 재시도 상태

### MVP 제외 (후속 단계)

- **영상 분석:** 프레임 추출, 클립 재생, 영상 업로드 및 영상 내 복수 생물 감지
- **지도·지구본:** GPS 기반 기록, 포인트 탐색, 위치 지도 표시
- **로그북/그림일기:** 다이빙 단위 기록, 수심·수온·장비·노트 편집
- **커뮤니티:** 공개 피드, 팔로우, 좋아요, 공유, 랭킹
- **나만의 바다 꾸미기:** 배경/장식 배치, 게임형 보상과 재화
- 오프라인 동기화, 전문가 검수 워크플로, 다국어, 종별 시즌/서식 통계
- 생성형 AI로 사용자별 매번 다른 그림 생성: MVP는 저작권/비용/품질을 통제하기 위해 승인된 종별 대표 일러스트를 사용

## 2. 사용자 흐름과 화면 명세

### 대표 사용자 흐름

1. 홈/도감에서 **발견 기록 추가**를 누른다.
2. 사진 촬영 또는 앨범에서 선택한다. 사진 미리보기에서 다시 선택/삭제할 수 있다.
3. 업로드 후 식별 중 화면을 본다. 앱을 닫았다 돌아와도 작업 상태를 다시 불러온다.
4. 후보 카드(국문명, 학명, 신뢰도 구간, 대표 이미지)를 확인한다.
5. 맞으면 후보를 선택한다. 다르면 종 검색으로 바꾸거나 **잘 모르겠어요**를 선택한다.
6. 종 카드 미리보기에서 사진·종·선택적 지역을 확인한다.
7. 저장하면 발견 기록 상세와 개인 도감으로 이동한다. 같은 종이면 기존 도감 항목의 발견 기록 수가 증가한다.

### 공통 UI 원칙

- 바텀 탭은 **도감 / 발견하기 / 설정** 세 개만 둔다. 발견하기는 중앙의 주 행동으로 강조한다.
- 한 화면의 주 행동은 하나로 제한하고, 한국어를 기본 언어로 한다.
- 수중 환경을 고려해 버튼은 크고 명확하게, 상태는 텍스트와 아이콘으로 함께 표현한다.
- 신뢰도는 “확실/가능성 있음/낮음” 같은 이해하기 쉬운 구간으로 표시하고, 근거 없는 정확한 퍼센트는 노출하지 않는다.

### 화면 목록·상태·요소

| 화면 | 주요 요소 | 상태 및 처리 |
|---|---|---|
| 1. 시작/로그인 | 서비스 설명, 둘러보기, 로그인/가입 | 첫 실행, 로그인 중, 인증 오류. 둘러보기는 샘플 데이터만 표시 |
| 2. 내 도감 | 수집 종 수, 종 카드 그리드, 검색, 발견하기 버튼 | 로딩 스켈레톤, 첫 기록 전 빈 화면, 결과 없음, 네트워크 오류/재시도 |
| 3. 사진 선택 | 카메라 촬영, 사진 보관함, 이용 안내 | 권한 미허용, 권한 거부(설정 이동 안내), 미지원 형식/크기, 사진 미리보기 |
| 4. 업로드/식별 중 | 진행 상태, 취소, 백그라운드 복귀 안내 | 업로드 중, 분석 대기, 분석 중, 완료, 시간 초과/재시도, 서버 오류 |
| 5. 후보 확인 | 후보 최대 3개, 이름/학명/신뢰도 구간, 사진 재확인, 다른 종 검색 | 후보 있음, 후보 없음, 저신뢰 안내, AI 실패 후 수동 검색/미확인 저장 |
| 6. 종 검색 | 검색 입력, 국문/학명 결과, 선택 | 검색 중, 결과 있음, 결과 없음, 검색 오류. 카탈로그에 없는 종은 미확인 저장 가능 |
| 7. 카드 저장 확인 | 그림책 대표 일러스트, 종 이름, 사용자 사진, 선택 지역(선택), 저장 | 저장 중, 저장 실패/재시도, 중복 종이면 “새 발견 기록 추가” 설명 |
| 8. 발견 상세 | 종 카드, 사용자 사진, 기록일, 선택 지역, 삭제 | 로딩, 없음/삭제됨, 오류. 삭제 확인 모달 |
| 9. 설정 | 계정, 개인정보 안내, 로그아웃, 계정/데이터 삭제 요청 | 로그인/비로그인, 삭제 진행/완료 안내 |

### 카드 표시 규칙

- **종 카드:** 카탈로그의 따뜻한 그림책 스타일 대표 일러스트 + 국문명 + 학명 + “발견 N회”.
- **발견 기록:** 실제 업로드 사진 + 발견 날짜 + 해당 종 + 선택적 지역. 사용자 사진은 종 카드 일러스트를 대체하지 않는다.
- AI가 확정하지 못한 기록은 **미확인 해양생물** 카드로 저장하며, 추후 종을 지정할 수 있도록 데이터 구조를 열어 둔다.

## 3. 데이터 모델 및 ERD 초안

### 관계 개요

```text
users 1 ─── N observations N ─── 0..1 species
                         │
                         ├── 1 media_assets
                         └── 1 identification_jobs ─── N identification_candidates ─── 0..1 species
species 1 ─── 1 species_artworks (MVP 대표 일러스트; 버전 확장 가능)
```

`observations.species_id`가 비어 있으면 미확인 기록이다. 사용자가 같은 종을 여러 번 기록해도 observation은 매번 새로 만들고, 도감 화면에서 `user_id + species_id`로 묶어 발견 횟수를 집계한다.

### 필드 초안

| 테이블 | 필드 | 설명/제약 |
|---|---|---|
| `users` | `id UUID PK`, `email`, `display_name`, `created_at`, `deleted_at` | 이메일 유니크(대소문자 정규화), 소프트 삭제 여부 검토 |
| `species` | `id UUID PK`, `slug UNIQUE`, `common_name_ko`, `scientific_name`, `description_ko`, `taxonomy_json`, `is_active`, `created_at`, `updated_at` | MVP 카탈로그. 학명은 유니크 강제 대신 별칭/동의어 테이블 확장 고려 |
| `species_artworks` | `id UUID PK`, `species_id FK`, `asset_key`, `thumbnail_key`, `style_name`, `license_source`, `created_at` | 앱이 공개 가능한 대표 일러스트만 참조. 원본 파일은 비공개 버킷/정적 CDN 정책에 따름 |
| `media_assets` | `id UUID PK`, `owner_user_id FK`, `storage_key UNIQUE` (정제 완료 최종 객체), `upload_storage_key UNIQUE NULL` (서명 PUT 원본 객체), `mime_type`, `byte_size`, `width`, `height`, `sha256`, `status`, `captured_at NULL`, `created_at`, `expires_at`, `deleted_at`, `storage_deleted_at NULL` | GPS EXIF 제거. 원본과 정제 파일을 별도 키에 저장해 아직 유효한 PUT URL의 재사용이 정제 사진을 덮어쓰지 못하게 한다. 삭제 요청은 즉시 비공개 처리하고 worker가 객체 삭제 성공까지 재시도 |
| `identification_jobs` | `id UUID PK`, `user_id FK`, `media_asset_id FK`, `status`, `provider`, `model_version`, `error_code NULL`, `created_at`, `started_at NULL`, `completed_at NULL` | status: `queued/running/succeeded/failed`; 공급자 응답 원문 전체 저장은 피함 |
| `identification_candidates` | `id UUID PK`, `job_id FK`, `species_id FK NULL`, `rank`, `score NULL`, `confidence_band`, `label_raw NULL` | rank 1~3, `score`는 내부용. 외부에는 구간화된 값만 표시 |
| `observations` | `id UUID PK`, `user_id FK`, `species_id FK NULL`, `media_asset_id FK`, `identification_job_id FK NULL`, `identified_by`, `region_label NULL`, `observed_at`, `created_at`, `updated_at`, `deleted_at` | `identified_by`: `ai_confirmed/user_selected/unidentified`; 시간은 UTC 저장, 앱에서 현지 표시 |

### 인덱스·무결성 초안

- `observations(user_id, created_at DESC)` 목록 조회용
- `observations(user_id, species_id, created_at DESC)` 종별 발견 횟수/목록용
- `identification_jobs(user_id, created_at DESC)` 최근 처리 내역용
- `identification_candidates(job_id, rank)` 후보 순서 조회용
- 모든 사용자 소유 리소스는 API에서 `owner_user_id`를 검증한다. UUID를 안다고 다른 사용자의 사진/기록에 접근할 수 없어야 한다.
- 관측 기록의 종 변경은 허용하지만, 변경 이력은 MVP에서 감사 로그 대신 `identified_by`와 현재 선택을 기록한다. 운영/정정 요구가 생기면 이력 테이블을 추가한다.

## 4. 백엔드 API 초안

기본 규칙: `/v1`, JSON, Bearer 인증. 사진 업로드는 사전 서명 URL을 사용해 앱에서 오브젝트 스토리지로 직접 보낸다. API 서버는 파일 본문을 중계하지 않는다. 모든 오류는 `{ "error": { "code": "...", "message": "...", "request_id": "..." } }` 형식이다.

| 메서드·경로 | 목적 | 요청/응답 핵심 |
|---|---|---|
| `POST /v1/auth/register` | 가입 | `{email, password, display_name?}` → `{user, access_token}` |
| `POST /v1/auth/login` | 로그인 | `{email, password}` → `{user, access_token}` |
| `GET /v1/me` | 내 계정 | `{user}` |
| `DELETE /v1/me` | 계정/기록 삭제 요청 | 비동기 처리 여부와 완료 안내 반환. 삭제 정책은 개인정보 안내와 일치 |
| `POST /v1/media/upload-intents` | 업로드 URL 발급 | `{mime_type, byte_size, sha256?}` → `{media_id, upload_url, expires_at, required_headers}` |
| `POST /v1/media/{media_id}/complete` | 업로드 완료 확인 | 서버가 객체 존재/소유권/크기를 확인 → `{media_id, status}` |
| `POST /v1/identification-jobs` | 식별 시작 | `{media_id}` → `202 {job_id, status}`. 업로드 완료 미디어만 허용 |
| `GET /v1/identification-jobs/{job_id}` | 작업/후보 확인 | `{status, candidates:[{species, confidence_band}], fallback_available, error_code?}` |
| `GET /v1/species?query=` | 종 검색 | 국문명·학명 검색 → `{items:[species + artwork]}` |
| `GET /v1/species/{species_id}` | 종 상세 | 종 설명/대표 그림책 일러스트 메타데이터 |
| `POST /v1/observations` | 발견 저장 | `{media_id, species_id?, identification_job_id?, observed_at?, region_label?, identified_by}` → `{observation, species_summary?}` |
| `GET /v1/observations?cursor=&limit=` | 내 발견 기록 | `{items, next_cursor}`. 사용자 소유 기록만 반환 |
| `GET /v1/observations/{id}` | 발견 상세 | 사진/종/날짜/지역 |
| `PATCH /v1/observations/{id}` | 종/지역/날짜 수정 | 소유권 확인 후 허용 필드만 변경 |
| `DELETE /v1/observations/{id}` | 발견 삭제 | 기록 소프트 삭제 후 사진 참조 여부 확인, 고아 파일 정리 작업 등록 |
| `GET /v1/collection` | 내 도감 요약 | `{items:[{species, discovery_count, first_seen_at, latest_seen_at}], total_species}`. 미확인은 별도 항목 |

### 비동기 식별 계약

- `POST /identification-jobs`는 빠르게 `202`를 돌려주고, 앱은 1~2초 간격 폴링 후 완료/실패 시 멈춘다. 작업이 길어지면 최대 대기 후 재시도 버튼을 제공한다.
- 중복 탭/재전송을 고려해 `Idempotency-Key`를 저장 생성 요청에 지원한다. 식별 작업은 동일한 media/job을 중복 생성하지 않도록 기본 멱등 처리한다.
- AI 응답이 없거나 실패해도 `species_id` 없이 발견 기록 저장이 가능해야 한다.
- 후보 이름은 카탈로그 종에 연결할 수 없으면 `species_id = null`과 원시 라벨만 내부에 보관하고, 사용자에게는 검색 가능한 종만 보여준다.

### 업로드 정책 기본값

- JPEG/PNG/HEIC 허용 여부를 실제 이미지 라이브러리와 AI 공급자 지원에 맞춰 확정한다. 개발 MVP는 JPEG/PNG를 기준으로 하며 HEIC은 앱에서 JPEG 변환이 검증된 뒤 허용한다.
- 사진 한 장 최대 15MB, 긴 변 기준 2048px 리사이즈된 분석용 파생 이미지 생성. 원본 보관은 최소화하고 목적/보관 기간을 정한다.
- 사전 서명 URL은 짧은 만료 시간, 사용자·미디어 ID에 묶고, 업로드 후 서버가 파일 형식/크기/해시를 확인한다.

## 5. 앱·서버·AI 구성 제안

```text
Expo 앱 ── HTTPS API ── FastAPI ── PostgreSQL
   │                         ├── 작업 큐/워커 ── AI 식별 공급자
   └── 사전 서명 업로드 ───────────────┴── S3 호환 오브젝트 스토리지
```

### 모바일 앱

- **React Native + Expo + TypeScript**: 한 코드베이스에서 iOS/Android 화면과 사진 선택을 구현한다.
- **Expo Router**로 화면 경로를 구성하고, 서버 데이터는 **TanStack Query**로 로딩/재시도/캐시를 다룬다.
- 폼/응답 스키마는 **Zod**로 검증한다. API 클라이언트는 OpenAPI에서 생성하거나 타입을 서버 계약과 함께 관리한다.
- 처음에는 디자인 시스템을 과하게 만들지 말고 색상, 간격, 버튼, 카드, 빈 상태 컴포넌트만 공통화한다.

### 서버 및 저장소

- **FastAPI**: 요청 검증, 인증/인가, 업로드 URL 발급, 종/발견 기록 API.
- **PostgreSQL**: 관계 데이터와 트랜잭션. 초기에 벡터 DB 불필요.
- **S3 호환 스토리지**(예: 운영 배포 대상 클라우드의 오브젝트 스토리지): 원본/파생 사진 및 일러스트 파일.
- **작업 처리:** 초기 개발은 DB 기반 작업 테이블과 별도 worker 프로세스로 단순하게 시작한다. 사용량/재시도 요구가 확인되면 Redis 큐를 도입한다.
- **마이그레이션:** Alembic. API 문서/OpenAPI를 앱 계약의 기준으로 둔다.
- 인증은 검증된 인증 라이브러리/관리형 서비스를 사용한다. 비밀번호를 직접 저장할 경우 Argon2id 등 안전한 해시와 토큰 만료/갱신 정책을 구현한다.

### AI 식별

- 초기에 자체 모델 학습은 하지 않는다. 우선 범용 비전 모델 또는 해양생물 전문 API를 **어댑터 뒤에 감싸서** 검증한다.
- 공급자 응답을 `{catalog_species_id, score, raw_label}` 내부 표준으로 변환한다. 공급자를 바꿔도 앱/API 계약은 유지한다.
- 모델이 반환한 이름을 그대로 종으로 확정하지 않는다. 30종 카탈로그 매핑이 없거나 신뢰도가 낮으면 후보 없음/저신뢰로 처리한다.
- **사전 검증 게이트:** 자체 수중 사진 최소 200장(종별·탁도·거리·조명 편차 포함)을 사람이 라벨링해 top-1/top-3 일치율과 미지원 종 오탐을 측정한다. 낮은 확신을 억지로 반환하지 않는 임계값을 정한다. 정확도 수치와 검증 표본은 출시 전에 제품 화면/내부 대시보드에서 추적한다.

## 6. 저장소 구조와 기술 선택

초기에는 한 저장소(monorepo)로 앱/API/문서를 함께 관리한다.

```text
ocean-diary/
  apps/
    mobile/                 # Expo 앱
  services/
    api/                    # FastAPI API
    worker/                 # AI 식별 및 이미지 후처리
  packages/
    api-client/             # OpenAPI 기반 TS 클라이언트(필요 시 생성)
  infra/
    docker-compose.yml      # 로컬 PostgreSQL 및 개발 의존성
  docs/
    product/                # 이 문서, 화면 흐름, 정책 결정
    api/                    # OpenAPI 설명/예제
    adr/                    # 기술 선택 결정 기록
  data/
    species/                # 카탈로그 CSV/JSON 원본 및 출처 메모
  .env.example
  README.md
```

### 선택 이유와 운영 원칙

- 서버 개발자가 API/DB부터 빠르게 시작할 수 있으면서 앱 화면은 한 코드베이스로 익힌다.
- 앱과 서버는 같은 저장소에 두되 배포/의존성은 각각 분리한다. 프론트엔드 학습을 위해 화면 단위 작업을 세분화하고 각 화면에서 상태 예시를 먼저 만든다.
- `main`은 항상 실행 가능한 상태로 두고 짧은 기능 브랜치/작은 PR 단위로 합친다.
- `.env`와 스토리지 키, AI 키는 저장소에 커밋하지 않는다. `.env.example`에는 변수명과 샘플 형식만 둔다.
- 로컬 개발은 Docker Compose의 PostgreSQL + API + worker를 기본값으로 한다. 모바일은 Expo 개발 서버를 사용한다.
- 초기 배포는 관리형 PostgreSQL/스토리지와 단일 API/worker 배포로 시작한다. 쿠버네티스나 마이크로서비스 분리는 현재 규모에서 보류한다.

## 8. 첫 주 작업 순서 및 완료 기준

첫 주의 목표는 완성된 앱이 아니라 **저장소에서 앱과 API가 실행되고, 샘플 종 데이터와 API 계약을 통해 첫 화면 개발에 막힘이 없는 상태**다. 서버 개발자인 사용자가 백엔드 기반을 잡고, 모바일은 화면 1~2개를 실제 기기/시뮬레이터에서 열어보는 것을 목표로 한다.

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1일차 오전 | 저장소와 폴더 생성, README, 기본 환경변수 | 새 환경에서 README만 보고 앱/API 구조와 실행 방법을 이해할 수 있음 |
| 1일차 오후 | API/DB 로컬 실행, health endpoint | API가 DB 연결 상태를 포함한 정상 응답을 반환 |
| 2일차 오전 | Expo 앱 생성 및 첫 실행 | iOS 시뮬레이터 또는 Android 에뮬레이터/기기에서 시작 화면 표시 |
| 2일차 오후 | 탭/도감 빈 화면과 샘플 카드 | 로딩/빈 상태/샘플 카드가 각각 구분되어 표시 |
| 3일차 오전 | 종·일러스트·미디어·발견·식별 ERD와 마이그레이션 | 빈 DB에서 마이그레이션과 30종 샘플 시드가 재현 가능 |
| 3일차 오후 | OpenAPI 초안과 API 클라이언트 연결 | 종 목록/검색 API를 앱에서 호출해 카드 목록 표시 |
| 4일차 | 사진 선택 화면과 업로드 API 계약/개발용 업로드 | 권한 거부와 사진 선택/취소가 화면에서 명확하게 처리됨 |
| 5일차 오전 | 식별 작업 상태/후보 API mock 및 후보 화면 | AI 없이도 후보 있음·저신뢰·실패 3가지 화면을 확인 가능 |
| 5일차 오후 | 이번 주 범위 정리, 위험/결정 기록, 다음 주 이슈 생성 | 다른 개발자가 저장소를 받고 30분 안에 앱과 API를 실행하며, 다음 작업이 티켓으로 정리됨 |

### 첫 주 산출물

- 실행 가능한 monorepo와 README
- 모바일 앱의 도감 빈 화면/샘플 종 카드
- API health check, 종 카탈로그 조회/검색
- DB ERD에 대응하는 첫 마이그레이션과 샘플 30종 데이터
- 사진 선택/업로드 및 AI 후보 화면의 와이어 수준 구현 또는 연결 가능한 목업
- 다음 주에 이어서 할 티켓: 인증, signed upload, 식별 worker, 저장 플로우

**첫 주에 하지 않을 것:** 모델 정확도를 제품 수준으로 최적화하거나, 지도·영상·로그북·커뮤니티·꾸미기를 구현하지 않는다. AI 공급자 계약 전에는 화면/API 흐름을 mock 결과로 병렬 개발한다.

## 10. 바로 시작할 첫 작업

**오늘 할 일은 저장소 뼈대, 앱/API 최소 실행, 종 카탈로그 30종 초안 작업 티켓을 만드는 것**이다. 첫 화면에서는 빈 도감과 샘플 종 카드를 먼저 구현한다. AI 공급자를 고르기 전에 업로드부터 저장까지의 계약과 수동 확인 경로를 확정하면, AI 검증이 지연되어도 앱의 핵심 경험 개발은 계속할 수 있다.

**MVP 완료 정의:** 로그인 사용자가 수중 사진 한 장을 올리고, AI 후보 또는 수동 종 선택을 확인한 뒤, 따뜻한 그림책 스타일 종 카드와 실제 발견 사진이 개인 도감에 저장되며, 앱을 다시 열어 기록을 확인하고 삭제할 수 있다. 영상·지도·로그북·커뮤니티·나만의 바다 꾸미기는 이 정의에 포함하지 않는다.
